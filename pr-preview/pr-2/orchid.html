orchid: github issues as an agent scheduler

Orchid is a very small scheduler for coding agents. The queue is GitHub issues. The worker runtime is tmux. The output is a pull request.

I wanted a way to run a bunch of coding agents without inventing a new place to work.

Most agent orchestration systems immediately grow a dashboard, a queue, a job schema, a log viewer, a state database, a callback server, and then a second dashboard to debug the first dashboard.

Orchid does less. Open an issue, add a label, get a PR.

issue → label → tmux → branch → pull request

It is one Go binary wrapped around gh, git, ssh, and tmux. State is a JSON file. Config is HCL. There are no webhooks.

Issues are already a queue

GitHub issues are a pretty good work queue if you stop trying to make them something else.

They have:

  • title and body
  • labels
  • comments
  • authors
  • timestamps
  • links to PRs
  • notifications
  • permissions

That is already more product surface than most queue dashboards.

Orchid uses an inbox repository. Labels route issues to real repositories:

target "deno" {
  label = "deno"
  repo  = "denoland/deno"
}

target "clawpatrol" {
  label = "clawpatrol"
  repo  = "denoland/clawpatrol"
}

An inbox issue labeled deno becomes a branch in denoland/deno. An inbox issue labeled clawpatrol becomes a branch in denoland/clawpatrol.

The target repository stays normal. Humans still review PRs in the place where they review PRs. The weird scheduler lives off to the side.

The ABI is text

When Orchid assigns work, it starts a terminal and pastes a prompt.

You are implementing GitHub issue #151:
"node compat: fix async_hooks promise lifecycle for absent tests"

Work repo: denoland/deno
Worktree: /home/orchid/orch-work/issue-151
Branch: orch/divybot-151

--- issue body ---
...
--- end issue body ---

Commit, push, open a PR, then stop and wait.

That is the whole worker protocol.

There is no SDK. No agent plugin. No JSON-RPC channel. If a model can read a terminal and type commands, it can be a worker.

This is nice because coding is not a single request. It is a long-running mess: a checkout, failed tests, half-applied patches, background builds, CI failures, review comments, and a shell full of evidence. The terminal keeps that mess in one place.

When CI changes, Orchid pastes the update into the same pane. When someone comments on the PR, Orchid pastes that too. The agent can inspect, amend, push, and stop again.

tmux is enough runtime

Each worker is a tmux session:

tmux new-session -d \
  -s claude-151 \
  -c /home/orchid/orch-work/issue-151 \
  clawpatrol run -- claude --dangerously-skip-permissions

This sounds crude until something breaks.

Then crude is excellent.

tmux capture-pane -p -t claude-151 -S -80
tmux send-keys -t claude-151 "retry the push; github ssh is fixed" Enter
tmux respawn-pane -k -t claude-151 -c /home/orchid/orch-work/issue-151 \
  "clawpatrol run -- claude --resume"

The dashboard shows the polite version: issue number, target repo, branch, PR, latest checks, and pane output.

tmux is the truth.

If the dashboard is wrong, capture the pane. If Orchid dies, tmux is still running. If a worker is confused, type into the pane. If a session needs to be restarted, respawn it in the same worktree.

I like systems where the emergency debugger is the same tool I use during normal operation.

The poll loop

Orchid polls GitHub every tick.

for issue in open inbox issues:
  if issue has a target label and no job:
    allocate a vm slot
    create a worktree
    spawn a tmux pane
    paste the bootstrap prompt

for job in state.jobs:
  discover PR by branch
  relay new comments
  relay new review threads
  relay CI transitions
  teardown when the PR closes

Webhooks would make this look more professional. They would also add a public endpoint, a secret, a retry story, local tunnel setup, and another failure mode.

For pull request work, thirty seconds of latency is fine.

Capacity is a number

A machine has slots.

vm "local" {
  host        = "localhost"
  capacity    = 30
  session_cmd = "clawpatrol run -- claude --dangerously-skip-permissions"
}

When all slots are full:

issue #139: no free VM, skipping

That is the queue backpressure story.

This only works because the tasks are small. The issue should not be “make Node compat good”. It should be:

node compat: implement inspector Network domain enough for HTTP/fetch tests
node compat: don't queue Promise destroys in FinalizationRegistry
clawpatrol: bound response bodies read during OAuth device flow

Small issues give the agent a narrow surface and a clean definition of done. Large issues turn into archaeology.

The state file

Orchid remembers the minimum amount of information needed to keep talking to the right pane.

{
  "jobs": {
    "151": {
      "tmux": "claude-151",
      "target_repo": "denoland/deno",
      "branch": "orch/divybot-151",
      "pr": 34247,
      "last_head_oid": "f65ee970...",
      "last_check_conclusions": {
        "lint title": "SUCCESS",
        "test node_compat (3/3) release linux-x86_64": "FAILURE"
      }
    }
  }
}

That file answers:

  • which issue owns this pane?
  • which branch did it push?
  • which PR did that branch become?
  • which CI transitions have already been pasted?
  • which comments and reviews have already been relayed?

It is not a distributed database. It is a memory of what Orchid has already said out loud.

The ugly parts are useful

The first version of Orchid had the bugs you would expect from a physical machine pretending to be a scheduler.

Do not kill tmux when restarting Orchid.

Do not close the inbox issue just because the work PR moved.

Do not paste the same failing CI result forever.

Do not respawn every stuck pane in one tick and stampede the network.

Do not let a worker sit at Claude’s resume picker and call it “running”.

Do not assume GitHub SSH inside the agent sandbox is the same as GitHub SSH on the host.

That last one was especially funny in the bad way. The workers were alive, the daemon was alive, but github.com inside the sandbox resolved to a synthetic address. The agents kept trying to push through the wrong path. From the outside it looked like “the model is stuck”. From tmux it was just ssh timing out during banner exchange.

The fix was not a better prompt. It was pinning GitHub SSH to a real GitHub IP, cleaning known_hosts, and retrying the pushes.

Most “agent reliability” problems are like this. The model is the weird part, so it gets blamed first. Usually the bug is a stale process, a missing credential, a bad remote, a flaky test, or a command still running in the background.

Clawpatrol is the boundary

Orchid starts workers under Clawpatrol.

That part matters. Once agents can clone repositories, run tests, push branches, open PRs, and read issue comments, the question is no longer “can it code?”. The question is “what can this process reach while it is coding?”

Orchid decides what should run:

issue #165 -> denoland/clawpatrol -> orch/divybot-165 -> PR #568

Clawpatrol decides what the worker can touch while it runs:

api.anthropic.com     allow with credential injection
github.com           allow with GitHub credential
postgres.internal    deny destructive SQL, approve mutations
slack.com            only if the profile has that credential

The split is important.

Orchid should not know how to approve packets. Clawpatrol should not know what a good PR looks like.

The human stays in the loop

Orchid does not remove review. It removes babysitting.

The human still decides what work is worth doing, how narrow the issue should be, whether the patch is tasteful, and when to merge.

Orchid owns the boring loop:

open issue → spawn pane → get PR → relay feedback → free slot

That is enough machinery for a swarm.
